OSC.008 extends OSC.007 on fixed C arrays into pointer parameters, byte-buffer boundaries and explicit nonce encoding. A small proof-of-work exercise makes the differences visible: an array owns contiguous storage, while a function receiving its pointer must be told the valid length. The earlier C functions lesson covered parameter passing and return values, and the loops lesson supplied repeated trials.

The exercise extends our OSITC.015 malware-cost lesson and the original Proof-of-Power Wall article. The important boundary remains unchanged: a puzzle can discourage some mass automated requests, but solving it does not establish identity, safe intent or freedom from viruses.

Learning objectives

  • Pass a bounded byte buffer through a pointer parameter and track its length explicitly.
  • Explain why an array often converts to a pointer when passed to a function.
  • Encode a 32-bit nonce as four bytes with an explicit byte order.
  • Use OpenSSL to calculate a SHA-256 digest and check a low-difficulty work target.
  • Separate a local coding demonstration from a secure, production admission gateway.

Pointer parameters and binary buffer boundaries

An array such as unsigned char message[64] reserves 64 contiguous bytes. The expression sizeof message reports the array's storage size in its defining scope. When passed to a function, an array expression ordinarily converts to a pointer to its first element; the callee must receive or otherwise know the length separately. The C array language reference describes the conversion and its exceptions.

The challenge occupies the first bytes; four subsequent bytes encode a nonce in big-endian order. Before copying, the program checks whether challenge length plus four exceeds the destination capacity. The guard prevents an out-of-bounds write, one common route to memory corruption in unsafe C programs.

Compile and verify a small real hash puzzle

The example uses OpenSSL's EVP_Digest API rather than implementing SHA-256 manually. A 16-bit zero-prefix target succeeds with probability 1 in 65,536 per independent random-looking digest. The expected number of attempts is approximately 65,536, although any particular run can finish earlier or later.

#include <stdint.h>
#include <stdio.h>
#include <string.h>
#include <openssl/evp.h>

static int has_zero_prefix(const unsigned char *digest, unsigned bits) {
    unsigned full_bytes = bits / 8;
    unsigned remaining = bits % 8;
    for (unsigned i = 0; i < full_bytes; ++i) {
        if (digest[i] != 0) return 0;
    }
    return remaining == 0 || (digest[full_bytes] >> (8 - remaining)) == 0;
}

int main(void) {
    const unsigned char challenge[] = "demo-only";
    const size_t challenge_len = sizeof challenge - 1;
    unsigned char message[64] = {0};
    unsigned char digest[EVP_MAX_MD_SIZE];
    unsigned digest_len = 0;

    if (challenge_len + 4 > sizeof message) return 1;
    memcpy(message, challenge, challenge_len);

    for (uint32_t nonce = 0; ; ++nonce) {
        message[challenge_len]     = (unsigned char)(nonce >> 24);
        message[challenge_len + 1] = (unsigned char)(nonce >> 16);
        message[challenge_len + 2] = (unsigned char)(nonce >> 8);
        message[challenge_len + 3] = (unsigned char)nonce;

        if (EVP_Digest(message, challenge_len + 4,
                       digest, &digest_len, EVP_sha256(), NULL) != 1)
            return 1;
        if (digest_len == 32 && has_zero_prefix(digest, 16)) {
            printf("nonce=%u first_digest_bytes=%02x%02x\n",
                   nonce, digest[0], digest[1]);
            return 0;
        }
        if (nonce == UINT32_MAX) break;
    }
    return 1;
}

On Linux with a C compiler and OpenSSL development headers installed, save the program as pow_demo.c and run cc -std=c11 -O2 -Wall -Wextra -Werror pow_demo.c -o pow_demo -lcrypto, followed by ./pow_demo. A tested execution printed nonce=67571 first_digest_bytes=0000. The loop starts at nonce zero and examines one candidate per iteration.

Why a hash prefix is not an antivirus

The fixed demo-only challenge, missing expiration and absent replay database make the example intentionally unsuitable for a real gateway. An attacker can reuse a known answer. Production admission requires unpredictable server challenges, per-request binding, time limits, replay prevention, authentication, rate limits and resource exhaustion safeguards.

Tor's onion-service proof-of-work defense is a real service-level example that prioritizes clients under denial-of-service pressure. It does not inspect executable malware or replace system protections. Our coverage of API validation and Lowery's Softwar argument provides further context on the difference between request cost, policy enforcement and strategic security theories.

Knowledge check

  • Question: Why must a function receiving a byte buffer also know its length? Answer: Pointer conversion does not preserve the original array size for the callee.
  • Question: Why is a fixed challenge insecure? Answer: A valid nonce can be reused without performing new work.
  • Question: Does a successful hash imply a malware-free device? Answer: No. It demonstrates computation, not endpoint integrity.
