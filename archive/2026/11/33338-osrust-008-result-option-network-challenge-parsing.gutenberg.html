Result separates valid values from errors

Rust's standard library defines Result<T, E> with success and failure variants. A function can return Ok(value) when a request parses cleanly or Err(error) with a precise reason for rejection. Unlike unwrap(), which can panic, ? returns early from the current function when the operation fails.

An Option represents an existing value with Some or its absence with None. Calling split_first() on an empty slice produces None; ok_or() converts that absence into an explicit parse error. Pattern matching remains available when a caller needs a different action for each error variant.

Parse a bounded request with no external crates

The demonstration uses a six-byte request: one version byte, one effort byte and a four-byte unsigned nonce in network byte order. An effort field is only a parameter in the example; accepting it does not prove that any hashing work was performed. Rust's safe slice methods reject truncated input before attempting to convert the nonce.

#[derive(Debug, PartialEq, Eq)]
struct ChallengeRequest {
    version: u8,
    effort_bits: u8,
    nonce: u32,
}

#[derive(Debug, PartialEq, Eq)]
enum ParseError {
    ShortInput,
    UnsupportedVersion,
    InvalidEffort,
    TrailingBytes,
}

fn parse_request(input: &[u8]) -> Result<ChallengeRequest, ParseError> {
    let (&version, rest) =
        input.split_first().ok_or(ParseError::ShortInput)?;
    let (&effort_bits, payload) =
        rest.split_first().ok_or(ParseError::ShortInput)?;

    if version != 1 {
        return Err(ParseError::UnsupportedVersion);
    }
    if !(4..=20).contains(&effort_bits) {
        return Err(ParseError::InvalidEffort);
    }

    let nonce_bytes: [u8; 4] = payload
        .get(..4)
        .ok_or(ParseError::ShortInput)?
        .try_into()
        .map_err(|_| ParseError::ShortInput)?;
    if payload.len() != 4 {
        return Err(ParseError::TrailingBytes);
    }

    Ok(ChallengeRequest {
        version,
        effort_bits,
        nonce: u32::from_be_bytes(nonce_bytes),
    })
}

fn main() {
    for data in [
        &[1, 16, 0, 1, 7, 0][..],
        &[1, 16, 0][..],
        &[1, 32, 0, 1, 7, 0][..],
    ] {
        println!("{:?}", parse_request(data));
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn parses_valid_request() {
        assert_eq!(
            parse_request(&[1, 16, 0, 1, 7, 0]),
            Ok(ChallengeRequest {
                version: 1, effort_bits: 16, nonce: 0x00010700
            })
        );
    }

    #[test]
    fn rejects_truncated_request() {
        assert_eq!(
            parse_request(&[1, 16, 0]),
            Err(ParseError::ShortInput)
        );
    }

    #[test]
    fn rejects_extra_bytes() {
        assert_eq!(
            parse_request(&[1, 16, 0, 1, 7, 0, 5]),
            Err(ParseError::TrailingBytes)
        );
    }
}

Boundary checks do not replace authentication

An attacker might send a valid six-byte header and still intend harm. A production gateway needs server-generated unpredictable challenges, expiration, replay prevention, an actual cryptographic verifier, authentication, authorization and resource limits. Cloudflare's server-side validation documentation illustrates the independent need to verify admission tokens instead of trusting a browser alone.

Knowledge check

  • Question: Why use Result for a parser? Answer: Invalid input is expected and must be reported without a process crash.
  • Question: Does Ok(ChallengeRequest) prove a valid work solution? Answer: No. It proves only that the header met the parser's format rules.
  • Question: What prevents reading past the input? Answer: Safe slice access, explicit length checks and early error returns.
